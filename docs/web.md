# web — `mpt web`

[![CI](https://github.com/korosu/mpt-autopilot/actions/workflows/ci.yml/badge.svg)](https://github.com/korosu/mpt-autopilot/actions/workflows/ci.yml)
[![Python 3.10+](https://img.shields.io/badge/python-3.10%2B-blue.svg)](https://www.python.org/downloads/)
[![License: MIT](https://img.shields.io/badge/license-MIT-green.svg)](../LICENSE)

A local browser interface for every other `mpt` stage: pick a command, fill in
its flags, watch the log arrive line by line, see the exit code.

Single user, on localhost, **no authentication**. It runs stages as child
processes, which is exactly what the CLI does — so anyone who can reach the port
can render and upload videos. Keep it on `127.0.0.1`.

---

## Install

Flask and psutil are optional dependencies, so the core CLI stays at four
packages:

```bash
uv sync --extra web
```

`mpt --help` and `mpt web --help` work without it; only actually serving the
page needs Flask. psutil powers the "runs started outside this page" list —
without it the page still works, that one list just reports itself unavailable.

---

## Usage

```bash
mpt web                                  # http://127.0.0.1:8765
mpt web --port 9000
mpt web --no-browser                     # for an SSH tunnel
mpt --config /srv/mpt/config.yaml web    # a config somewhere else
```

| Flag | Default | Meaning |
|---|---|---|
| `--host ADDR` | `127.0.0.1` | Interface to bind. Loopback on purpose. |
| `--port N` | `8765` | Port to listen on. |
| `--no-browser` | off | Don't open a browser window on start. |

The same `--config` is passed to every child process, so the page can never run
a stage against a different config than the one it was started with. Editing
`config.yaml` from the browser is deliberately not a feature.

## What the page shows

One button per stage in the left sidebar — `refill`, `init-seen`, `batch`,
`enrich`, `upload`, `run`, `validate` — and for the selected one, **every flag
its `add_arguments()` registers**. Everyday flags are visible; the rest sit
under *Advanced*.

The controls are generated by introspecting the real argparse parsers at
runtime, so there is no second list of flags to keep in sync. Add a flag to a
stage and it appears on the page.

| argparse | Control |
|---|---|
| `store_true` | checkbox |
| `type=int` | number input |
| `choices=[...]` | select — or **toggle chips** when `action="append"`: click to select, click again to deselect |
| `--lang` with metavar `LANG`/`CODE` | language picker built from `config.yaml`'s `langs:` |
| `nargs="?"` | checkbox *(pass the flag)* plus an optional value box |
| everything else | text input |

`mpt enrich --lang` is a plain text box, not a picker: it takes an LLM language
name (`English`, `ru`), not a `config.yaml` language code.

A live preview under the buttons shows the exact command that will run.

**Fill from config** writes into every stage's fields the values your
`config.yaml` implies for them, and clears the rest — the result is each stage
exactly as the config describes it, never a mix with what was typed before.
**Reset** is the same pass with nothing to write, which lands on the blank page
state.

There are two pairs, with two scopes. The pair in the header works on **every
stage at once**: press it once, then switch tabs — the fields are already
filled, because what survives a tab switch is the fill, not the fields (the form
is rebuilt per stage). The pair in the form's action row works on **the open
stage only**, for when you want just that tab from the config.

Only keys the config actually sets are filled, and each is resolved the way the
stage itself resolves it: the stage's own section first, then the shared
`paths:` block, then the stage's own fallback (so `batch` shows
`jobs_dir/jobs.yaml` when no `batch.jobs` is set). A key the config never
sets leaves its field empty — the input's placeholder already shows the
argparse default, so nothing is filled in twice.

`batch` also takes a **video count** (`--limit N`): how many videos to generate
before the run stops. Jobs already seen or disabled never consume the count, a
video recovered from an interrupted run does, and whatever is left stays queued
for the next run. `mpt run` carries the same knob as `--batch-limit N` — its own
`--limit` belongs to the uploader, so the two stay distinct flags.

Above the form, a one-line map — **refill → batch → enrich → upload** — doubles
as navigation and shows where the selected stage sits in the pipeline. The dots
on the right of the header report the current run's state (idle, running with
elapsed time, or how the last run ended) and the MoneyPrinterTurbo API's state
(green `/ping`, amber "not MPT", red "nothing there"). A first-time explainer
sits under the map; ignore it after that.

## One run at a time

The Run buttons lock while a stage is in flight, and a second start returns
`409`. Two concurrent stages would deadlock on the same `seen.txt` file lock,
race each other's jobs files, and queue against one MoneyPrinterTurbo server.

The lock lives inside the web process. It does not stop a `mpt batch` you start
by hand in a terminal — the stages' own file locks still cover that — but the
page now *sees* such a run, read-only, under the form (see below).

## Runs started outside this page

A `mpt` run started in a terminal or by cron is listed under the form: its
stage, PID, start time, and — when it provably uses this page's `config.yaml`
(the `--config` it names, or the `./config.yaml` in its working directory) —
the tail of that stage's file log. `batch` writes `logs/batch.log` and `enrich`
writes `logs/enricher.log`; `refill`, `upload` and `init-seen` keep no file log,
and a `mpt run` shows both. The list refreshes every 10 s.

Detection, not control: the page cannot cancel a run it did not start, and the
run has to be on the same machine as `mpt web`. A process whose command line
merely mentions the project (an editor with `cli.py` open, a shell wrapping
the real invocation) is not listed — only `mpt` itself and
`python -m mpt_autopilot.cli` count.

## Cancelling

**Cancel** kills the child *and its children*: `taskkill /F /T` on Windows,
`SIGTERM` to the process group elsewhere. A bare `terminate()` would leave a
running `youtubeuploader` behind, and a half-cancelled upload is worse than no
cancel button.

On POSIX the group gets `SIGKILL` after a 10-second grace period if the child
ignored the `SIGTERM` — a process that survives the graceful signal would hold
the run slot forever. On Windows `taskkill /F` is already forceful.

`batch` recovers from a kill through its in-progress registry, so the next run
picks the state back up.

---

## Reloading mid-run

Safe. The log is buffered server-side (the last 5000 lines), the page is
delivered with the current run's state, and `EventSource` resends
`Last-Event-ID` on reconnect — so the stream resumes where it left off instead
of restarting blank. Closing the tab does not stop the run.

Beyond 5000 lines the start of the log is dropped from the buffer; the stage's
own file log (see `logger.py`) always has the whole thing.

## Is MoneyPrinterTurbo up?

The header's second dot answers that, so the page never looks healthy while the
render server is gone. Every ~15 s the page asks `GET /api/mpt-status`, which
probes `{batch.api_url}/ping` with a 2 s timeout.

MPT ships that endpoint itself: `GET /ping` answers `pong`
(`app/controllers/ping.py`, upstream and in local installs alike; it sits
outside the `x-api-key` protection, which covers only `/api/v1` and `/tasks`).
The dot has three states, because "something answered" and "MoneyPrinterTurbo
answered" are different facts:

| Answer | Dot | Text |
|---|---|---|
| `200 pong` | green | `MPT API: up (host, latency)` |
| any other HTTP code | amber | `MPT API: no /ping, HTTP 404 — not MoneyPrinterTurbo? (host)` |
| refused / timed out | red | `MPT API: down (host)` |
| no `batch:` section | grey | `MPT API: not configured` |

The amber state is the one worth reading twice: the port is taken by a server
that is not MoneyPrinterTurbo — a hardened fork guarding `/ping`, or another
service on the same port — so `mpt batch` would fail against it no matter how
healthy that server is. A config with no `batch:` section reads "not
configured".

How MPT runs is irrelevant to the check: tmux, systemd or a bare terminal all
expose the same HTTP port, and `mpt batch` reaches the same URL from the same
config — if a render could reach it, the probe can too.

## Errors

| Situation | What you see |
|---|---|
| exit code 1 | red banner, log stays on screen |
| exit code 2 | amber banner — stopped on quota |
| cancelled | grey banner |
| invalid form | red banner with the reason; **no process was started** |
| second run | `409` — a run is already in progress |
| server died mid-submit | red banner, the Run button is usable again |
| MPT API unreachable | the header dot turns red — `mpt batch` would fail the same way |
| MPT API answers, but not `/ping` | the header dot turns amber — that port is not MoneyPrinterTurbo |
| request to an unexpected Host | `403` — the DNS-rebinding guard |
| Flask missing | `[ERROR] mpt web needs Flask — run: uv sync --extra web` |
| `config.yaml` missing | the same `[ERROR]` every other stage prints |
| cross-origin POST | `403` |

Stages print their own `[ERROR]` lines and return their own exit codes; the page
adds nothing but the banner. No tracebacks reach the browser.

Non-ASCII output survives: the child runs with `PYTHONIOENCODING=utf-8` and is
read with `errors="replace"`, mirroring `cli._force_utf8_output()`.

## Security

There is no login. Three things stand between the page and the outside world:

- it binds `127.0.0.1` unless you override `--host`, and answers only that
  host plus the loopback spellings — a rebound attacker domain gets `403`, not
  a runnable page. The `Origin` check alone cannot catch this: a rebound host
  sends a `Host` and an `Origin` that match each other perfectly;
- a POST carrying an `Origin` header that isn't this server is refused with
  `403`, so a page on another site can't start an upload for you;
- the embedded spec JSON is rendered with Flask's `| tojson`, so no argparse
  help string or `config.yaml` label can close the `<script>` tag and inject
  markup.

Werkzeug will warn that it is a development server. For one person on loopback
that is fine. Don't put it on a public interface.

## How it fits together

```
browser                  Flask (threaded)              child process
───────                  ────────────────              ─────────────
  POST /api/run   ──▶  argv.build_argv()  ──▶  Runner.start()
  ◀── 202 {run_id}                              │ one-slot lock
                                                ├─▶ python -m mpt_autopilot.cli
  EventSource      ──▶  Runner.subscribe()      │      --config CFG <stage> …
  ◀── event: line  ◀──  buffer + Condition  ◀───┤ reader thread
  ◀── event: end   ◀──  proc.wait()         ◀───┘
  POST /api/cancel ──▶  kill the process tree
```

| Module | Responsibility |
|---|---|
| `web/spec.py` | argparse introspection → flag spec. Pure; loads no settings. |
| `web/config_defaults.py` | config.yaml → the per-stage values "Fill from config" writes. Mirrors the stages' own resolution order; never raises. |
| `web/argv.py` | form + spec → `list[str]`. The only place input becomes a command. |
| `web/runner.py` | the run slot, the pipe reader, the line buffer, cancellation. |
| `web/status.py` | the MPT `/ping` probe. Pure httpx; no Flask. |
| `web/external.py` | process scan → runs started outside the page, read-only. |
| `web/app.py` | Flask routes and SSE. Thin. |
| `web/cli.py` | `mpt web` itself. Imports Flask lazily. |

Arguments are always passed as a list with `shell=False`, so a value like
`en; rm -rf /` stays one opaque string.

## API

| Route | Contract |
|---|---|
| `GET /` | the page, with the flag spec and current state embedded |
| `GET /api/status` | `{busy, run_id, stage, exit_code, cancelled, started_at}` |
| `GET /api/mpt-status` | `{configured, up, reachable, status_code, latency_ms, api_url, host}` |
| `GET /api/external` | `{scanner: "psutil"\|"unavailable", runs: [{pid, stage, started, command, logs}]}` |
| `POST /api/run` | `{stage, flags}` → `202 {run_id, command}` / `400` / `409` |
| `GET /api/stream/<run_id>` | `text/event-stream`: `line`, `end`, keepalive comments |
| `POST /api/cancel` | `202`, or `409` when nothing is running |

`/api/mpt-status` probes on every call — one user polls it every ~15 s, so a
cache would only make the dot lag behind reality.

## Limits

- One run at a time, by design.
- No `config.yaml` editing.
- No run history — each start clears the pane; past runs live in the stage logs.
- The "runs started outside this page" list is read-only and same-machine only;
  without psutil in the `[web]` extra it reports `unavailable` rather than
  guessing.
- `mpt web` does not appear as one of its own buttons.
